# Acme IT Support Agent

一个 AI IT 支持 agent，用来替代"提 ticket 然后等"。员工用自己的话描述问题；agent 在公司的各个系统里调查，修复它被允许修复的问题，其余的交给对应的人工团队，并附上完整的交接，让员工不必把同样的事再说一遍。

所有东西都在本地运行，对接一家模拟公司 "Acme"：15 个服务、23 篇知识库文章、14 名员工、incident、变更记录、22 张历史 ticket 和一份 policy 文件。

## 1. 问题和范围

**用户：** 遇到 IT 问题的员工，不是 helpdesk 人员。他们知道症状（"Okta 登不进去"），不知道原因。

**为什么做这个问题：** 大多数 IT ticket 是重复的、有文档的（账号锁定、VPN、权限申请、已知故障），但每一张都要排队，等一个人去查同样的记录。agent 一分钟就能做完这些调查。

**交互方式：** 聊天。网页 UI 左边是对话，右边是每一次 tool 调用、推理摘要、case 记录和交接 ticket；另附一个终端 CLI。agent 本身只有一个方法 `respond(message)`，接入 Slack 或 Teams 不需要改它。

**成功的样子：** 几分钟之内，问题修好了，或者员工清楚知道接下来会发生什么，而且不用填任何表。已知故障：一条回复里就知道不是自己的问题、workaround 和 ETA。转人工：拿到 ticket 编号，知道哪个团队接手、首次响应的目标时间，交接里已经有他说过的话和 agent 查到的东西。

| 领域 | agent 自己解决 | 交给人工 |
|---|---|---|
| 登录（Okta） | 账号锁定：从登录日志找到原因，验证身份后解锁，说明怎样避免再次被锁 | MFA 重置、账号停用 |
| 应用（Salesforce 等） | 已知 incident：记录显示员工在影响范围内，并且员工自己说出的情况符合 incident 的描述时，把员工加入 incident，给出 workaround 和 ETA；有 KB 解法的单人问题 | 检查后原因仍不明 |
| VPN | 旧客户端的 bug：用连接日志和已安装版本确认，征得同意后推送批准的版本 | 网络侧的问题 |
| 权限 | 自动批准的权限当场开通；需要审批的提交给正确的审批人 | 不能申请的权限（生产库写权限） |
| 数据 pipeline | 诊断：把失败和维护窗口里的变更联系起来 | 修复（防火墙、重跑），附上证据 |
| 安全 | 立即的安全步骤 | 钓鱼、设备丢失：一律以 P1 转给 Security Operations |

## 2. 为什么需要 agent

同一个症状，对不同的人原因不同，要同时看好几个数据源才能分清：

- "我重置了密码还是登不进去"：对这位员工来说，是 iPhone 上的 Outlook 还在用旧密码重试，把账号又锁了。只有登录日志能看出来；FAQ 搜索只会返回她已经试过的密码重置文章。
- "Salesforce 很慢"：对 Chicago 办公室的人是已知 incident，对 New York 的人是浏览器问题。答案取决于 incident 的影响范围和员工的位置。
- "上周五以后 Jenkins 一直超时"：需要变更记录、任务的报错，以及说明哪种报错对应哪项变更的 runbook。

规则引擎要求每条路径提前写好，遇到新问题就失效；基于 KB 的聊天机器人看不到员工的记录，也不能动手。agent 决定**下一步查什么、问什么**；每个 case 都不能变的部分（谁能做什么、身份是否已验证、什么算证据、交接格式、优先级）由 code 决定。

## 3. 架构和设计决定

```
员工 ──► web / CLI ──► HelpdeskAgent.respond() ──────────────────────► 回复
                            │  对话 + case 记录（由 code 维护）
                            ▼
                      Claude（tool use 循环）
                            │ tool 调用
                            ▼
            tool runtime：校验输入、失败重试一次、读取结果分配 evidence id
                  │ 读 tool                              │ 写 tool
                  ▼                                      ▼
      KB · 状态/incident/变更 · 员工目录 ·       policy engine（policy.yaml + 身份状态）
      诊断 · 历史 ticket（经 facts.py）           allow / needs_approval / human_only / forbidden

      回复发出前：code 检查（引用的 KB 读过、编号存在）→ 第二个模型检查有没有没依据的说法 → 不过就退回重写
```

| 部分 | 决定什么 |
|---|---|
| Claude（`agent.py`、`prompts.py`） | 查什么、问什么、怎么解释 |
| Facts（`facts.py`） | 关于员工的每一个事实，比如已安装版本、已有权限、incident 是否覆盖员工 |
| Policy engine（`policy.py`、`data/policy.yaml`） | 一个动作能否执行、是否需要审批或人工 |
| Case 记录（`case.py`） | case 状态（只在 `transition()` 里改变）、每种结局的条件、ticket 的团队和优先级 |
| 回复检查（`checker.py`） | 一条回复能不能发出去：有没有编造流程、说错员工的话或记录、说做了其实没做、把"可能"说成"肯定" |

主要的设计决定：

- **约束放在 code 里，选择留给 model。** code 守住不变量（policy、身份、证据、交接格式），路径由 model 选择。全程用状态机控制的设计被放弃了，因为它遇到没人预料到的问题就会失效。
- **每个事实、每个决定只有一个负责的地方。** policy 和 tool 调用同一个 fact 函数，所以 agent 被告知的内容和 code 允许的操作不会矛盾。离线 test 检查这一点。
- **改动需要员工的原话。** 任何改动都要员工用自己的话同意这一项改动，验证码不算同意；`resolved` 需要员工在最后一次改动之后说"好了"的原话。
- **tool 输出是文字，并说明自己的局限。** 写入结果写明做了什么、读回的结果和没有改什么；不是实时的记录写明时间。
- **回复发出前再查一遍。** prompt 里写了"不要说没有依据的话"，模型还是会顺手补上一般公司的常见做法（"你可以直接回复 ticket"），这些在我们的系统里并不成立。能用 code 判断的（编号、读没读过 KB）由 code 检查；判断不了的，由一个便宜的模型（Haiku，不开思考）对照 tool 结果和规则，逐句判断有没有害，有害就退回重写，每轮最多两次。3 句以内的短回复不查。代价是每轮多约 2 秒，网页上可以随时关掉（"Verify replies"）。
- **单 agent、手写循环**（Anthropic SDK，不用框架），每一步都看得见、讲得清。
- **可观测性和成本：** 每个 case 一份 JSONL trace；网页通过 SSE 实时显示每一步，包括检查器打回的原因；prompt caching 让大部分输入 token 走缓存；eval 报告按 agent、检查器、模拟员工、judge 分开记花费。Model 是 `claude-sonnet-5-5`，可用 `AGENT_MODEL` 切换。

## 4. 自己解决还是转人工

边界写在 `data/policy.yaml` 里，不在 prompt 里：

| 决定 | 例子 | agent 怎么做 |
|---|---|---|
| `allow`（加前提条件） | 解锁账号（已验证、确实被锁）；开通自动批准的权限；推送批准的版本（员工同意）；加入 incident（记录里员工所在地在范围内，并引用员工在 agent 查到 incident 之后确认的情况） | 执行，并读回结果 |
| `needs_approval` | Snowflake PROD 读权限 | 提交给正确的审批人，以 `pending_approval` 结案 |
| `human_only` | MFA 重置、账号停用、防火墙、生产任务重跑 | 转给 policy 指定的团队 |
| `forbidden` | 本地管理员权限 | 解释原因，提供批准的途径（Self Service） |

agent 也会在这些情况下转人工：安全事件、检查后原因不明、证据矛盾、数据源一直失败、修复无效、员工要求找人。

**交接**（`var/tickets/IT-xxxxx.json`，UI 里也会显示）包括：员工说过的每一句话的原文；身份是否已验证；系统、症状和截止时间；agent 已经做了什么；每条发现及其 evidence id；还在考虑和已排除的原因；支持工程师需要回答的具体问题；已给出的 workaround；由 code 计算的优先级。model 只写摘要和判断，其余由 code 从 case 记录里填。

## 5. 数据源（模拟）

| 数据源 | 文件 | 用途 |
|---|---|---|
| 知识库和 runbook | `data/kb/*.md` | 有依据的修复步骤（其中一篇已废弃，用来测试过滤） |
| 服务状态、incident、变更记录 | `data/services.json`、`incidents.json`、`changes.json` | 已知故障及其影响范围；"最近改了什么" |
| 员工目录和诊断数据 | `data/users.json` | 部门、设备和版本、权限、账号状态、登录和 VPN 日志 |
| 历史 ticket | `data/tickets.json` | 可能原因的参考（其中一张埋了 prompt injection） |
| Policy 和权限目录 | `data/policy.yaml` | agent 能做什么、需要什么前提、谁来审批 |

每个示例问题都需要至少两个数据源才能答对，而且有些数据源互相矛盾（状态页说 Jenkins 正常，但每次运行都失败）。

## 6. 假设和取舍

- demo 的时间固定在 2026-10-22 14:30 UTC，让"昨天""上周五"和数据对得上。记录里的时间都是 UTC，tool 结果同时给出员工的本地时间，模型不用自己换算。
- 员工不需要 Okta 就能打开 helpdesk 聊天（比如在手机上用 Slack）。查记录不需要额外验证；账号和权限的改动需要短信验证码（模拟）。网页上的员工选择框代表这次登录。
- agent 只能看到当前登录员工自己的记录。
- 模拟数据是静态 JSON，每段对话一份独立副本。所以新开的对话看不到之前建的 ticket；转交之后员工怎么跟进（谁通过什么渠道联系他），这个模拟公司没有定义，agent 只说 ticket 编号、团队和首次响应的目标时间。
- 没有后台通知：加入 incident 不会在修好时通知员工，agent 也不会这样承诺。
- 记录和员工说法矛盾时，agent 不选边，交给人判断。
- KB 检索用 BM25：只有 23 篇文章时，embedding 的收益不大。
- 加入 incident 要员工确认：记录里只有他平时在哪个办公室，此刻在哪查不到。所以 agent 要先问，并引用员工在它查到 incident 之后说的话，code 才放行。
- 回复检查用延迟换准确：每轮多约 2 秒，换来盲测集里有害说法从 27% 的运行降到 3%（见第 8 节）。

## 7. 如何运行

需要 Python 3.10+ 和一个 Anthropic API key。

```bash
cd it-helpdesk-agent
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env        # 然后把你的 key 填进 .env

python -m helpdesk.web      # 打开 http://127.0.0.1:8000
```

在网页上选择以哪位员工的身份登录（14 位员工都能选，部分有示例问题），然后输入。**Fault injection** 菜单可以让某个 tool 超时或失败。**Verify replies** 开关控制回复检查，对话中途也能切换。验证码会以黄色系统通知出现，把它输入到聊天里即可。

终端：`python -m helpdesk.cli --trace`（`--user u-maya` 跳过选择；`/case` 打印 case 记录）。

Test：`python -m pytest -q`。Eval：`python -m evals.run_evals --repeats 3`（调优集）；`--file heldout.yaml` 跑盲测集；`--judge all|code-passed|off` 控制 judge 评哪些运行。

## 8. 如何评估

1. **单元 test**（`tests/`，75 个，不调用 model）：policy 决定、身份验证、同意、结案条件、故障注入、交接、优先级，以及"每个决定只有一个负责的地方"。
2. **场景 eval**（`evals/scenarios.yaml`，20 个场景）：每个场景由一个模拟员工（Claude Haiku，带人设和隐藏信息）和 agent 对话到结束，然后：
   - **code 检查**最终状态：结局、团队、优先级、执行的动作和禁止的动作、必须出现和不能出现的内容；
   - **code 规则**检查每一条回复（`evals/rules.py`）：版本号、时间、设备编号、ticket 编号必须在 tool 结果或员工的话里出现过；引用的 KB 必须读过；说"已经做了"的动作必须真的执行过；不能承诺跟进或"不用再说一遍"；回复语言要和员工一致；
   - 能用规则判断的都交给 code，**judge model**（Claude Opus）只看 code 判断不了的：自由文本里没有依据的说法（并标出有害的）、诊断、交接质量、员工体验、是否闭环，以及员工中途纠正后能否调整。默认只评 code 已经通过的运行（`--judge code-passed`），code 判了失败的就不再花 judge 的钱；
   - 每个场景跑 3 次，报告 pass^3。

场景覆盖五个示例问题，以及 MFA、账号停用、本地管理员的压力、钓鱼、设备丢失、含糊的描述、邮箱满了、办公室故障、员工在家时不加入办公室的 incident、非 IT 请求、状态页不可用、prompt injection、要求找人，以及把验证码当成同意的陷阱。

3. **盲测集**（`evals/heldout.yaml`，11 个场景）：上面的场景是边改边写的，分数偏乐观。盲测集由一个只读过 `data/`、没看过 prompt 和代码的 session 按 KB 和 policy 写出期望，我复核了标注，不对着它调 prompt。一个盲测场景如果促成了改动，就移进调优集（发生过一次，见下）。

### 结果

Claude Sonnet 5.5，每个场景 3 次。"有害说法"指 judge 标出的、会误导员工或专员的说法：编造的流程、说错的记录、没做说做了、把可能说成肯定。

| | 调优集（20 × 3） | | 盲测集（11 × 3） | |
|---|---|---|---|---|
| | 不加回复检查 | 加回复检查 | 不加回复检查 | 加回复检查 |
| 执行了禁止的动作 | 0/60 | 0/60 | 0/33 | 0/33 |
| 结局或动作不对 | 3/60 | 0/60 | 0/33 | 0/33 |
| 回复有依据（judge） | 47/60 | 55/60 | 17/33 | 30/33 |
| **有有害说法的运行** | **9/60** | **1/60** | **9/33** | **2/33** |
| 每段对话耗时（中位数） | 16.9 秒 | 25.1 秒 | 16.9 秒 | 31.5 秒 |

几点说明：

- **动作层面在没见过的问题上同样可靠**，因为它由 code 保证（policy、前置条件、员工原话的门槛）。措辞层面只靠 prompt 时，在盲测集上明显变差（27% 的运行有有害说法），加了回复检查后降到 6%。之后又给检查器加了超时和 agent 的 tool 列表，再跑一次盲测集：有害说法 1/33。
- **延迟**：表里加回复检查的耗时来自第一版检查器（会思考、每条都查）。后来关掉思考、3 句以内不查，一次不完整的盲测运行（31 段对话）里，agent 自己的耗时相对不加检查是 +25%（第一版是 +66%）。检查器改成逐句判断"有害或没问题"之后的效果，因为 API 额度用完，还没有在线验证。
- **花费**（盲测集，judge 评每一次运行）：每段对话 agent $0.051（其中检查器 $0.002），judge $0.046，模拟员工可以忽略，合计约 $0.10。judge 几乎占了评测费用的一半，所以默认只评 code 已经通过的运行。
- 最近一次盲测有 3 次结局不对：2 次是模拟员工（Haiku）跳出角色或没报告结果就离开；1 次是经理替下属求助时，agent 转交给了 Identity & Access，期望写的是拒绝或只给说明。我认为这次转交说得过去，但没有改标注。

### 剩下的失败

- **把推测说成事实**仍然偶尔出现，比如"Network 可能会要你提供业务理由"没有标明是自己的猜测，或者没查过 Laptop 服务就说"没有相关 incident"。回复检查能拦住大部分，拦不住全部。
- **一问多答**：有时一条回复问两个问题（规则只统计，不判失败）。

### 评测本身踩过的坑

judge 判为失败的运行，我都会对照 trace 复核。复核中发现过几个测量问题，修好之前的数字都不可信：

- 模拟员工（Haiku）先思考再回答，400 个 token 用完时没写出任何文字，runner 当成员工离开，替它说了句再见。最多 34 次运行因此"提前结束"。现在上限是 4000，空回复直接报错。
- judge 原来看不到 agent 的规则，会把"我只能看登录者本人的记录"判成没有依据，同时又放过了 prompt 明令禁止的"it isn't your laptop"。现在 judge 能看到规则。
- 规则在 383 段旧对话上回测时，发现检查器打回后，agent 的重写会引用一篇没读过的 KB，而重写不再经过 code 检查。现在每次重写都重新检查。

### 改动是怎么定下来的

每个改动都对应一个看到的失败，并重跑受影响的场景。几个例子：

- **"你不用再说一遍"**：system prompt 开头和转交 tool 的说明都把它写成了目标，模型就原样转告员工，不管细节收齐没有（10-29 的运行里 20 次转交都这么说）。删掉这两处之后，23 次转交里 0 次，交接评分没有下降。
- **没做的改动**：曾经想让 code 根据读过的 KB 检查交接字段。但读过一篇文章不代表它适用于这个问题，code 也只能检查字段在不在、检查不了内容真假，反而会逼 agent 编造。所以没加，只让 agent 在信息不够时当场补问，并用 `add_ticket_note` 补进 ticket。
- **盲测场景促成的改动**：一次盲测里 agent 把 13:40 UTC 说成纽约时间早上 6:40。现在 tool 结果直接给出员工的本地时间和日期，这个场景随之移进了调优集。

## 9. 如果有更多时间

- 在 CI 里跑 eval，按 prompt 版本跟踪每个场景的 pass^k；日常用便宜的 judge（先和 Opus 校准），关键节点再用 Opus，judge 用 Batch API。
- 回复检查分级：只在高风险的轮次（转交、结案、执行动作之后）拦截，其他轮次先发出、后台检查，进一步压低延迟。
- 定义转交后的跟进渠道，并让新对话能按编号查到自己的 ticket。
- 模拟员工换成更稳的模型，减少跳出角色造成的误判。
- 模型调用集中到一层 provider 接口，方便换模型或供应商。
- KB 文章质量的闭环：agent 已经记录没有答案的搜索和有问题的文章，把它们转给文章负责人。
- 主动跟进：incident 修好后通知员工，员工说没好就重新打开 case。
- 真实系统对接、SSO 和审计。见 `docs/design_note.md`。

## 代码结构
